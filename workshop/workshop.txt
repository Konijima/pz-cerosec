# The Steam Workshop item, as the game's own submit screen reads it.
#
# The format is SteamWorkshopItem.readWorkshopTxt (javap -p -c on the shipped
# projectzomboid.jar). Every line is trimmed; a blank one, or one starting with
# "#" or "//", is skipped, which is why these comments are legal. The keys it
# knows are id=, title=, description=, tags=, visibility= and version= (read and
# ignored). "description=" may repeat: each line is appended to the one before
# with a single newline between them (BootstrapMethods #9, "\1\n"), so a blank
# line in the description is a bare "description=" here. "tags=" is split on ";"
# and the legal set is media/WorkshopTags.txt, one tag a line. "visibility=" is
# one of public, friendsOnly, private, unlisted.
#
# "id=" is written by Steam after the first upload: the submit screen calls
# writeWorkshopTxt the moment you leave its second page, and that rewrite puts
# version=1 first, then id=, title=, one description= a line, tags= and
# visibility=. It does NOT keep these comments. Copy them back from git if you
# want them, and see docs/RELEASE.md for the rest of the checklist.
#
# ---------------------------------------------------------------------------
# THE IMAGES IN HERE, AND WHY THEIR URLS ALREADY WORK
#
# Steam renders [img] from a URL and has no idea what is inside the uploaded
# item, so nothing in the mod's own folder can be shown. Two hosts, and each
# has a reason:
#
#   * the banner and the nine section headers are served out of the PUBLIC
#     repository Konijima/pz-cerosec-media (a copy of workshop/banner.png and
#     workshop/img/), https://raw.githubusercontent.com/Konijima/pz-cerosec-media/
#     main/..., which answers with access-control-allow-origin: * and therefore
#     survives the crossorigin="anonymous" Steam puts on a third-party image.
#     The mod's own repository (Konijima/pz-cerosec) is public; whoever changes
#     an image here pushes the same file to pz-cerosec-media too (docs/RELEASE.md).
#
#   * the ten screenshots are uploaded to the ITEM, because that is where a
#     Workshop screenshot belongs -- it shows in the item's own gallery as well
#     as in the description. Their URLs do not exist until the upload, so each
#     pair has a commented slot below naming the two files from
#     workshop/SHOTS.md. They are prepared at 312 px wide, same as the banner
#     and the headers, so two of them sit side by side on the slot's line
#     the same way the banner's two panels do. Turning a slot on is one edit:
#     drop the "#", keep the "description=", and put the two image addresses
#     between their tags, a space apart.
#
# Every image in the description is authored at 312 px wide, measured on a
# real phone on 2026-09-17 (see below and docs/notes/workshop-study.md), not
# at the 630 px Steam's stylesheet allows:
#     .workshopItemDescription img { max-width: 630px; }
# (public/css/skin_1/workshop.css). 630 is a ceiling, not a target -- a
# section header is still just one <img>, alone on its line, but two 312 px
# <img>s sit side by side on the same line (an <img> is inline), which is how
# the banner and the paired screenshots below fill a desktop column of 655
# without ever being wider than a phone's.
#
# THE MOBILE STRETCH, AND WHY 312 FIXES IT WHERE 630 COULD NOT
#
# Confirmed 2026-09-17 by reading Steam's own served HTML and CSS on a mobile
# user agent: [img] renders as a bare <img>, no class, no width attribute
# (BBCode has none to give it), and the only rule that ever touches it is the
# 630px cap above. That rule is a ceiling, not a fill: on a phone narrower
# than 630 CSS px, nothing shrinks the image further, so a 630 px image
# overflows .workshopItemDescription and stretches the whole page sideways.
# Ruled out by the same read: no [table] is used here (a table would explain
# it, but there is none), and the [code] block's lines wrap
# (`div.bb_code { white-space: pre-wrap; }`), so they are not the cause
# either. There is no percentage-width or responsive fix available in Steam
# BBCode, so the only lever is the image's own pixel width -- and the
# narrowest phone column measured is 352 px, so authoring at 312 clears it
# with room, on a single column (headers, banner panels) or a pair (banner,
# screenshots) alike. tools/check-workshop.py holds every description image
# to exactly 312.
# ---------------------------------------------------------------------------
